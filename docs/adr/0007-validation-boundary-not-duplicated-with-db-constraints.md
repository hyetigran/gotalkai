# Where Zod validation stops and Postgres constraints take over

**Status:** accepted

Ticket #26's AC #3 asks explicitly: "Confirmed this validation is explicitly *not* duplicated between the app service and its own database — Postgres/ORM-level constraints are trusted there, per PRD §7.8's stated boundary." This records where that line is actually drawn, so future tickets don't accidentally blur it by adding an app-level "does this row exist" check that duplicates a foreign key.

**Decision:** Zod validates *shape* at the client/server API boundary — is this a well-formed UUID, a non-empty string, a valid enum value, a JSON body that parses at all. Zod does **not** validate *existence* — whether a given id actually refers to a row in the database. That's what foreign keys are for, and app-service's schema (ticket #19/#21) already has them (`sessions.learner_id`, `sessions.scenario_id`, `persona_memories.learner_id`, `observations.session_id`/`learner_id`, `debrief_items.observation_id`).

Concretely: `POST /sessions` with `{learnerId: "00000000-0000-0000-0000-000000000000"}` (a well-formed UUID for a learner that doesn't exist) passes Zod validation, then fails at the `sessions_learner_id_fkey` constraint when the insert runs — surfacing as the same generic database-error response (503) every other unexpected DB failure produces, not a bespoke "learner not found" check written in application code. `src/id-params.ts`'s `parseUuidParam` (and every request schema's `.uuid()` fields) only ever reject *malformed* ids; a syntactically valid id that happens not to exist sails through app-level validation and lands on the database's own constraint.

**Reasoning:** duplicating existence checks in the app layer is exactly the kind of thing that drifts out of sync with the schema over time — a new FK relationship added to `schema.sql` wouldn't automatically get a matching app-level check, and a removed one would leave a dead check behind. Trusting Postgres for this is also just correct: the database is the single source of truth for what exists, checking it from application code first is inherently racy (the row could be deleted between the app's check and its own insert) in a way the FK constraint itself is not.

**Consequences:** any new endpoint accepting an id that references another table should validate it as the right *shape* (Zod) and let the corresponding FK constraint (which must exist in `schema.sql` — if it doesn't, that's the actual gap to fix, not an app-level check) handle whether it *exists*. If a future ticket wants a friendlier response than a generic 503 for a specific FK violation (e.g., a proper 404 "learner not found" instead of "database unavailable"), that's a deliberate UX decision to make explicitly then — inspecting the Postgres error code and mapping it — not something to default into by adding existence pre-checks now.
