# Persona parameterization: registry design, Elena's authored identity, register choice, and memory partitioning

**Status:** accepted

Ticket #34 generalizes `persona.ts`/`persona-turn.ts` from Валентина-hardcoded to a real second persona (Елена Николаевна), and wires that generalization through the live pipeline (turn-orchestrator.ts, server.ts) and the data layer (`persona_memories`). This records the concrete design and the judgment calls PRD/the ticket text leave open.

## `persona_elena_prompt.md` does not exist — authored directly, same posture as Валентина's own identity prompt

PRD's own appendix (§ "Appendix — companion artefacts") lists `persona_elena_prompt.md` as a delivered companion file, "Persona 2 prompt (Елена Николаевна), Russian." It does not exist anywhere in this repo — confirmed by an exhaustive repo-wide search. This is the same situation `eval/identity-layer.txt` was in for Валентина's own identity prompt (also listed in that appendix, also never delivered): `persona.ts`'s `VALENTINA_IDENTITY_PROMPT` was authored directly from PRD §6.4's prose, not transcribed from a pre-existing file. Елена's identity prompt (`ELENA_IDENTITY_PROMPT`, `persona.ts`) is authored the same way, from the same posture — this is original content written for this ticket, not a verified pre-existing asset, and (like Валентина's) has had no native-speaker review.

**Source material used**, since PRD §6.4 only names Елена in the appendix table with no character description: `mobile/src/features/address-book/address-book-fixture.ts`'s `CAST_FIXTURE` entry for `'elena'` — already-committed, already-reviewed content from ticket #7's scripted Address book screen (itself ported from the original mockup, per that file's own doc comment). Her established characterization there: "Елена Николаевна," "Mother-in-law · school administrator," "A younger relative who talks fast and does not slow down for you. Idiom, elision," dials `[4, 3, 4]` (comprehension/production/repair, PRD §5.2's own scale), `formalCasualPercent: 50` (vs. Валентина's `22` — meaningfully more formal). The identity prompt is written to embody exactly this: a busier, more formal, faster-paced character who does not slow down or simplify for the learner the way Валентина does — the productive contrast AC #2 asks for ("her own register/dial calibration distinct from Валентина's ты/вы asymmetry").

## Register: mutual вы, not a reversed ты/вы asymmetry

Валентина's register (§6.4) is asymmetric: she uses ты (the learner is young to her), the learner uses вы (she is elderly). PRD doesn't specify Елена's register beyond AC #2's "distinct... calibration." A mother-in-law/school-administrator relationship reads as more formally charged than a grandmother-in-law's — not the *opposite* asymmetry (that would just be a mirror of the same mechanic), but a genuinely different register shape: **mutual вы**, both directions formal. This is a real, disclosed judgment call, not a PRD-specified fact — it's consistent with her higher `formalCasualPercent` in the existing fixture and gives the learner an actual second register pattern to practice (sustained formality, not just "who gets to be informal"), rather than reproducing Валентина's exact mechanic with the roles swapped.

## Dial calibration: the other half of AC #2, caught by review, not the original pass

AC #2 asks for Елена's "own **register/dial** calibration distinct from Валентина's ты/вы asymmetry" — the first draft of this ticket only made register persona-specific and left the "dial" half unaddressed entirely (ticket #36's `calibration_variant` system is keyed by learner segment, deliberately orthogonal to *persona* — a heritage-speaker learner gets the same dial defaults whether talking to Валентина or Елена, by that ticket's own design). A two-axis code review caught this as a real, undisclosed gap, not an intentional scope decision either ADR owned. Fixed with `app-service/src/personas.ts`'s `PERSONA_DIALS`: each persona's own **static** baseline dial characterization (comprehension load / production demand / repair behaviour), surfaced on `GET /learners/:id/address-book`'s `dials` field — distinct from, and layered independently of, a learner's own dynamic `calibration_variant`. Values are Валентина `[2, 2, 1]` / Елена `[4, 3, 4]`, taken verbatim from `mobile/src/features/address-book/address-book-fixture.ts`'s already-committed `CAST_FIXTURE` — the same source this ADR already draws Елена's identity-prompt characterization from, not new numbers invented for this fix.

## Registry design: `PersonaDefinition`, selected once per session via `session_start`

`voice-service/src/personas.ts` exports a small registry — `PersonaId = 'valentina' | 'elena'`, `PERSONA_DEFINITIONS: Record<PersonaId, PersonaDefinition>` (`systemPromptBlocks`, `personaRegister`, `learnerRegister`). `persona-turn.ts`'s `buildPersonaTurnRequest`/`generatePersonaTurn` take a `PersonaDefinition` parameter instead of calling `buildValentinaSystemPrompt()` directly — the one required signature change, and the reason AC #1 calls this "generalized," not "duplicated." `turn-orchestrator.ts`'s hardcoded `PERSONA_REGISTER`/`LEARNER_REGISTER` constants (added in ticket #29) become instance state instead, sourced from the active persona.

One persona per session, chosen once, matching the product's own framing ("talk to her daily," Address book §6.4) — not a mid-conversation switch. `TurnOrchestrator` is still constructed once per WebSocket connection (server.ts, unchanged from ticket #18/#29) with Валентина as the connection-time default — every existing test that never sends a `personaId` keeps exercising exactly the pre-#34 behavior, satisfying AC #1's "Валентина's existing behavior must be unaffected." A new `selectPersona(persona, voiceId)` method (same shape as ticket #29's `sessionStart(sessionId)`) is called from `session_start`'s handler when the message names a different persona, swapping the active prompt/register/voiceId in place before any turn runs.

`messages.ts`'s `session_start` schema gains an optional `personaId: z.enum(['valentina', 'elena']).optional()`. Voice-service resolves the *voice id* (an env-var-backed secret, not something `personas.ts` itself knows) and passes it into `selectPersona` — keeping `personas.ts` env-free, matching the existing separation between pure pipeline modules and `server.ts`'s env-reading role. `ELEVENLABS_ELENA_VOICE_ID` is a new **optional** env var (unlike Валентина's own required one) — no real ElevenLabs account exists in this environment to audition a voice for her either (same disclosed gap as docs/adr/0016 for Валентина's own voice pick), and making it required would force every deployment to configure a voice for a persona that may not have launched yet. If `session_start` names `elena` and the env var isn't configured, server.ts sends the existing `{type: 'error'}` message and leaves the connection on its current (Валентина) persona rather than crashing the connection — graceful degradation, matching every other vendor-configuration gap this codebase already handles this way.

## `persona_memories` partitioning: a new `persona_id` column, not a new table

PRD §8/ticket #34 AC #4: "Unlocking and switching personas preserves each persona's own separate `persona_memories` — Елена does not inherit or leak Валентина's memories." The table (ticket #19) has no persona concept at all today — every memory belongs only to a `learner_id`. Adding a `persona_id TEXT NOT NULL DEFAULT 'valentina'` column (the established idempotent `information_schema`-guarded `DO $$` pattern, matching `learners.audio_sampling_consent_at`/`scenario_complications.target_structure_key`) is additive and correctly classifies every pre-#34 row as Валентина's without a backfill migration — there is no other persona those rows could have belonged to. `recordPersonaMemory`/`selectAndMarkCallbackMemory`/`getPersonaMemoriesForLearner` (`persona-memories.ts`) all gain a `personaId` parameter and filter/write by it. `seedStarterMemories` (ticket #22/#30, called at learner creation) seeds Валентина's `persona_id` specifically — she's the only persona a new learner ever starts with; there is nothing to seed for Елена before B1 unlock, and seeding a locked persona's memories would be dead data with no session that could ever reference it.

## Address book: real B1-gating built server-side, not wired into the mobile screen

AC #3: Address book should show Елена sealed/next/reached from real `learner_structures` data, "not a hardcoded flag." A real endpoint and computation exist (`GET /learners/:id/address-book`, `address-book.ts`) — B1-readiness is read the same way ADR-0004's debrief-readiness proxy already does (no stored CEFR level exists anywhere in this schema; there never has been one), reusing `debrief-ranking.ts`'s own `READINESS_MASTERY_STABILITY` constant rather than inventing a second mastery threshold: a learner is B1-ready when at least `B1_READY_STRUCTURE_COUNT` (provisional, tunable — see the constant's own comment) of their tracked structures have reached that stability. **Not wired into the mobile Address book screen** — that screen (ticket #7) is still the scripted `CAST_FIXTURE` demo, and wiring it to a live endpoint requires the same real per-session credential issuance and live-data plumbing docs/adr/0017 already disclosed as blocked in this environment (no physical device, no live mic capture triggering any of this pipeline in the first place). This ticket builds the real, unit-tested server-side half; the client-side wiring is inherited scope from that pre-existing gap, not reopened here.
