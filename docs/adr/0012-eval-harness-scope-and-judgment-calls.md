# Eval harness: placement, judgment calls, and verification gaps

**Status:** accepted

Ticket #28 (PRD §10) builds the three-layer eval harness. PRD.md's own text underspecifies several concrete choices; this records what was decided and why, plus what could and couldn't be verified in this environment.

## Placement: `voice-service/src/eval/`, not a top-level `eval/`

PRD §10 says "Harness in `eval/`," which reads as a repo-root directory. This repo has no pnpm workspace (`pnpm-workspace.yaml` doesn't exist) — it's a monorepo *by convention*, three independent npm/pnpm projects (`mobile/`, `app-service/`, `voice-service/`) sharing one git repo, with no cross-package `import` resolution set up anywhere. AC #6 ("imports the same Zod schema from ticket #14") requires importing `personaTurnSchema`/`generatePersonaTurn` from voice-service's `persona.ts`/`persona-turn.ts`. Setting up a real pnpm workspace to let a root-level `eval/` import from `voice-service/` would be a structural, repo-wide change well beyond this ticket's scope. Placing the harness inside `voice-service/src/eval/` gets a real, working import (`../persona`, `../persona-turn`) via a plain relative path, using voice-service's existing jest/tsconfig/eslint setup as-is.

## Mapping PRD's 8 mechanical-assertion names onto 5 negative controls

PRD §10 lists eight items in one sentence ("Schema, turn length, register consistency, ё spelling, no English leakage, no praise, no grammar talk, recast fires when and only when it should") and separately says "**Five** negative controls carry disproportionate weight." PRD never names the five. This implementation reads "recast fires when and only when it should" as two distinct failure modes — firing when it shouldn't (a *false* recast) and failing to fire when it should (a *missed* recast) — giving five negatives: `no_false_recast`, `no_missed_recast`, `no_english_leakage`, `no_praise`, `no_grammar_talk`. The other three (schema, turn length, register consistency, ё spelling — actually four; "ё spelling" makes four, not that the count matters) are structural checks, not negative controls. `no_false_recast` is checked on every entry, not just clean-input ones — inventing a correction is wrong whether or not a real error was present, and is the specific failure PRD calls "the single most important assertion: a persona that invents grammar problems destroys the fiction."

"Weighted" is implemented as reporting priority (`no_false_recast` listed first among the mechanical assertions, per PRD's own framing), not a numeric scoring difference — the actual gate PRD specifies is binary ("0% mechanical errors," "0% false recasts"), not a weighted composite score, so there's no numeric weight for a "weighted" negative control to actually apply to.

## Judge model: Claude Opus 5, not Sonnet 5

PRD says only "frontier model." Using the same model being evaluated (Sonnet 5, ADR-0003) as its own judge risks self-grading bias — a different, stronger model reduces that. Opus 5 was chosen as the available stronger model in the SDK's `Model` type.

## `recast_quality` gate scoped to `shouldRecast` entries only

PRD's gate list just says "recast quality ≥ 4.0" without specifying which entries count. A "recast quality" score on an entry with nothing to recast isn't measuring the same thing as one on an entry with a real planted error — including it would dilute the gate with numbers that aren't answering the gate's actual question (was the correction executed well). `computeGates` (gates.ts) means-only over entries where `entry.shouldRecast === true`.

## `drift_cases_pass` gate scoped to mechanical results only, not judge scores

Similarly unspecified by PRD ("drift cases pass 100%" doesn't say pass *what*). `computeGates`'s `drift_cases_pass` gate checks only that every mechanical assertion passes for `isDriftCase` entries — it doesn't additionally require a judge-score floor. Reasoning: the mechanical layer is exactly what's meant to "catch instruction decay at turn 40" (PRD §10's own framing for why the golden set exists at all) — decay shows up as a negative control firing (false recast, praise, grammar talk, English leakage) or a structural check failing (register slipping, response ballooning in length), all mechanical. The judge's three dimensions are already covered for drift entries by the ordinary `grammaticality`/`recast_quality`/`register_character` gates over the whole set, so requiring a *separate* judge floor specifically for drift entries would just be re-testing the same scores under a different name, not adding a new check.

## `checkYoSpelling`: dictionary-based, not per-entry-predicted

The first draft added an optional `expectedYoWord` field to `GoldenEntry`, set per-entry to whatever ё-word a correct response was expected to use. No entry ever ended up setting it — predicting the exact word a generated response will use isn't reliable, so the field sat unused and the check was vacuous (always trivially passed, never actually exercised). Replaced with a small fixed dictionary of common ё-bearing words checked against *any* response (`YO_WORD_DROPPED_SPELLINGS`, mechanical-assertions.ts) — this is exercised by whatever any given response happens to contain, not tied to a prediction about one specific golden entry.

## Append-only enforcement: git-diff-based, not a hash ledger

A hash recorded in the same file being edited is trivially bypassed by updating both together. `append-only.ts` instead inspects the real `git diff` between an MR's target branch and `HEAD` — any removed/changed line in `golden-set.ts` fails the check (`isAppendOnlyDiff`), which is what "append only" structurally means. This is real, tooling-enforced blocking (wired as its own CI job, `.gitlab-ci.yml`'s `eval:golden-set-append-only`), not a convention — verified directly in `append-only.test.ts` against a real disposable git repo, not a mock of `git`.

## Golden-set content: authored directly, not native-speaker reviewed

The 22 entries (`golden-set.ts`) were authored directly for this ticket: 4 aspect, 3 motion-verb, 2 case-government, and 2 register entries from PRD §5.8's priority list, plus 1 gender-agreement entry, 3 clean/no-error entries (a `no_false_recast` control needs real negative cases to be meaningful), 4 adversarial-bait entries (English leakage ×2, praise, grammar-talk), and 3 drift cases (long context, PRD §10's "instruction decay at turn 40"). No native-speaker review has happened on this specific content — same disclosure as ticket #14's persona identity prompt. PRD §10 itself specifies periodic native-speaker review ("quarterly... on rubric changes") as the actual verification mechanism for content quality — this is a Phase-1-scale placeholder set, not a claim of linguistic authority.

**Undisclosed gap in an earlier draft of this ADR, corrected here:** PRD §5.8's priority list is aspect, motion verbs, **stress placement**, register, case government — five items. This golden set covers four of the five and substitutes a sixth category (gender agreement, not in PRD §5.8 at all) in place of stress placement, without having said so. That substitution wasn't arbitrary but it also wasn't disclosed, and `golden-set.test.ts` originally asserted "covers the PRD §5.8 priority structures" while only checking four of the five — a test that looked like it verified spec coverage but didn't. Both are fixed now: the test checks exactly what's covered (not a false claim of full coverage), and this paragraph says so directly.

**Why stress placement specifically is excluded, not just missing:** stress placement (PRD §5.8/§7.4) is a phonological property — which syllable is stressed — that doesn't appear in standard Russian orthography at all (Cyrillic text doesn't normally mark stress). `persona.ts`'s `text` field is plain, unstressed Cyrillic; stress marks only get added later by the stress-annotation pipeline stage (§7.4), which doesn't exist yet (blocked on #13's bake-off) and isn't part of what this harness evaluates. There is no textual "stress error" a learner turn could exhibit, and nothing in the persona's own text output for this ticket could exhibit a stress *correction* either — a golden entry "targeting" stress placement would have nothing real to check. This is a structural scope boundary of a text-only harness evaluating pre-stress-annotation output, not an oversight to fix by adding more entries; it should be revisited once the stress-annotation stage exists and has its own text-with-stress-marks output to evaluate.

## Verification gaps in this environment

- **No `ANTHROPIC_API_KEY`** (same as ticket #14/docs/adr/0010): `judge.ts` and the full `runEval` pipeline require real model calls. Orchestration logic (mechanical assertions, gate computation, report aggregation, the judge's request/response handling) is fully unit-tested against hand-rolled fakes matching the real SDK surface. Two live-gated tests (`judge.test.ts`, and `runEval` indirectly through `generatePersonaTurn`) will run for real the first time this suite executes somewhere with a key configured.
- **No CI runners registered on this GitLab project** (confirmed via `glab api projects/:id/runners` — empty list, and zero pipeline history on any branch merged so far this session). `.gitlab-ci.yml` is written correctly and will run the moment a runner is registered — for a project this size, likely GitLab's shared runners, which need enabling at the instance/group level, outside what this repo's code can provision. This means AC #7 ("harness runnable in CI") and UAT #4 ("confirm the harness runs in CI on a real PR/commit") are **not verified to actually execute** here, only written correctly. Both `eval:golden-set-append-only` and `eval:offline-tests` need no `ANTHROPIC_API_KEY` and would pass immediately once a runner exists; `eval:harness` (the real model-call run) additionally needs that secret configured in the project's CI/CD variables.
