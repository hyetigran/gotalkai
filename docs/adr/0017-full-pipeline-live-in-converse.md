# Full pipeline live in Converse: transport choice, AEC gap, and verification status

**Status:** accepted

Ticket #18 builds the real pipeline from #14-#17 into a live per-turn cascade (server) and a matching client-side hook and message layer (mobile). This records the architectural decisions made to do that, and is explicit about status: **none of this has run on a device, and the shipped Converse screen does not currently activate it at all** — see below for why. Per explicit product-owner direction (given the moved-up deadline, after #13's bake-off was already skipped), the instruction for this ticket specifically was "build the wiring anyway, flag it clearly as unverified" — this ADR is that disclosure, not a claim of working software.

## Audio transport: WebSocket message chunks, not a WebRTC peer connection

PRD's architecture diagram labels the mobile↔voice-service link "WS/WebRTC stream," and ticket #10's own code comment anticipated "later pipeline tickets that add real TTS playback and a peer connection reuse this [WebRTC] stream." Building that — a real `RTCPeerConnection` between the mobile client and a Node WebRTC peer in voice-service — is substantial, independent infrastructure (SDP/ICE negotiation, a server-side WebRTC stack voice-service doesn't have at all) that cannot be responsibly built blind, with zero ability to test signaling or media flow.

Instead, this ticket extends the **existing WebSocket connection** (`voice-service/src/messages.ts`, `mobile/src/lib/voice-service/voice-connection.ts` — ticket #11's skeleton) to carry audio as base64-encoded PCM chunks in both directions, alongside the existing `ping`/`pong` messages. This is consistent with how `stt.ts` (#15) and `tts.ts` (#17) were already built — both assume chunked audio in/out, not a raw media stream — so this choice doesn't retrofit anything, it's the transport those modules were already shaped for.

**Consequence: this does not get WebRTC's automatic echo cancellation.** PRD §7.10 says this explicitly: "WebRTC gives AEC free; raw PCM capture does not." `react-native-webrtc`'s `MediaStream` (acquired in ticket #10's `webrtc-local-audio-stream.ts`) only hands audio to a native `RTCPeerConnection` — it does not expose raw samples to JavaScript, so there is no way to route its AEC-processed audio into a WS-chunk protocol at all. The mic audio this ticket actually sends to STT comes from a *different* path (below), with no AEC applied. **Her own voice re-entering the mic during playback may be transcribed as the learner's speech** — this is a real, known, unaddressed risk, not a theoretical one PRD warns about in the abstract. A real fix requires the WebRTC-peer-connection path described above, out of scope here.

## Mic capture: no live raw-PCM source exists in this stack — capture is a disclosed stub

**Correction to this ADR's original text (written before the API was actually re-checked against source):** an earlier draft of this section claimed `AudioRecorder.addListener('audioSampleUpdate', ...)` / `setAudioSamplingEnabled()` as a real streaming-sample API. That was wrong. Reading `node_modules/expo-audio/build/AudioModule.types.d.ts` directly shows `setAudioSamplingEnabled`/`audioSampleUpdate` are declared on **`AudioPlayer`** (playback visualization — e.g. waveform display during TTS playback), not `AudioRecorder`. `AudioRecorder`'s only event is `recordingStatusUpdate` (`RecordingEvents`, used today for the level meter's metering poll); its only output is a file written by `record()`/`stop()`. There is no method on `AudioRecorder` that streams live float frames to JS.

Checking further: `RecordingOptions` does support `LINEARPCM` (`IOSOutputFormat.LINEARPCM`) file output on **iOS only** — `AndroidOutputFormat`/`AndroidAudioEncoder` offer only compressed formats (3gp/mpeg4/amr/aac/webm), no raw-PCM option on Android at all. And `react-native-webrtc`'s `MediaStream` (already confirmed above to not expose raw samples for the AEC discussion) has no audio-frame-sink API either — grepped for `AudioSink`/`onaudioprocess`/frame-callback patterns across the package, none exist.

So there is genuinely no way to get live raw PCM into JavaScript with this project's current dependencies, on either platform, without one of: (a) a new native module (not buildable or testable in this environment), or (b) a server-side WebRTC receiver (already rejected above as too risky to build blind), or (c) an iOS-only segmented-file polling hack (record short `LINEARPCM` segments, stop/read/send/restart) that has no Android equivalent and real audible gaps at segment boundaries.

**Decision (explicit product-owner call, given the deadline):** mic capture is left as a **disclosed stub**, not a fake implementation. `mobile/src/features/converse/pcm-encode.ts` (float frames → downmix → 16-bit PCM → base64) is built as real, pure, unit-tested logic — its correctness doesn't depend on where frames come from, and it's ready for whatever eventually supplies them. But nothing calls it with real microphone data anywhere in this ticket — there is no code that even attempts to source live frames, because no such source exists (see above), so there's no meaningful call site to mark with a TODO. Consequence: the server-side pipeline (VAD → STT → persona → TTS) can never be triggered from the mobile client in this environment, because it's never sent any audio to trigger on — everything downstream of the stub is real, wired, unit-testable code that is structurally unexercisable without either a native capture module or revisiting the WebRTC decision.

## TTS playback: `data:` URI per sentence chunk, unverified

ElevenLabs returns each sentence's audio as a base64 MP3 blob (`tts.ts`'s `TtsChunk.audioBase64`). Playback (`mobile/src/features/converse/use-tts-playback.ts`) uses `expo-audio`'s `createAudioPlayer`, whose `AudioSource` accepts a plain string — a `data:audio/mpeg;base64,<...>` URI is passed directly rather than writing each chunk to a temp file via `expo-file-system`. Chunks are queued and played sequentially in receipt order (the wire protocol already guarantees `tts_chunk` arrives in sentence order within a turn), advancing on the player's `playbackStatusUpdate`/`didJustFinish` event. This is real, unit-tested logic (against a fake player, since there's no native-module mock for `expo-audio` anywhere in this repo — same reason `use-mic-capture.ts` has never had a test). Whether iOS/Android's underlying player actually accepts `data:` URIs for audio (as opposed to only `http(s)://`/`file://`) is **not verified** — this is exactly the kind of detail that needs a device to confirm. If it doesn't work, the fallback is writing each chunk to a temp file and using a `file://` URI instead — more code, but a more universally-supported source type.

## Why `converse-screen.tsx` still runs the scripted demo, not the live hook

`mobile/src/features/converse/use-live-converse-session.ts` is a complete, real, independently-tested replacement for `use-converse-session.ts` — it drives `phase`/`turns`/hold-to-think off actual `VoiceConnection` server messages (persisting the single `hasFloor` check from docs/adr/0002), and owns TTS playback via `use-tts-playback.ts` above. It is **not** wired into `converse-screen.tsx` as the active hook. Two independent reasons, either one alone sufficient:

1. **No mic capture source exists at all** (see above) — the live pipeline can never be triggered by anything the mobile client does, regardless of how the screen is wired.
2. **No real per-session credential issuance exists.** `voice-connection.ts`'s own established rule (ticket #11, unchanged by this ticket): the auth token is passed in by the caller, never read from a bundled env var, "until the app service exists to issue real per-session credentials (ARCHITECTURE.md §6)." That issuance still doesn't exist — `POST /sessions` returns only `{status, id}`, no voice-service credential. Building it is real, separate, ticket-scale work (app-service minting short-lived per-session tokens, voice-service validating them instead of the current shared-secret placeholder), out of scope here. Baking the shared secret into the mobile bundle to work around this would violate an existing, deliberate security rule — not something this ticket's "build the wiring anyway" direction was asking for.

Given (1) alone already makes any wiring into the screen unexercisable in principle, spending further effort connecting the screen to a credential source that doesn't exist wouldn't make anything more real — it would just be additional UI plumbing on top of an already-inert path. `use-live-converse-session.ts` and `use-tts-playback.ts` are built and tested standing alone, ready to be wired in once both blockers are separately resolved.

## What's real vs. what's unverified, summarized

**Built as real, working code, independently unit-tested:**
- Message protocol extending `messages.ts` (audio chunks, turn lifecycle, hold-to-think control, timestamps), plus the server sending `transcript_final` and `transcript_partial` (PRD §6.2: "learner's transcribed turn" / live "what did I just say" feedback) — real gaps found and fixed during this ticket's own review, not just disclosed ones
- Server-side turn orchestrator wiring VAD → STT → persona LLM → stress annotation → TTS, with six-timestamp instrumentation, in-character filler on generation latency, and the "she doesn't understand you" mechanic keyed off STT word confidence
- Barge-in state handling (stop TTS, cancel LLM generation, reset turn state) — PRD §7.10's "cancel in-flight TTS"/"cancel LLM generation" is *logical* cancellation (in-flight results are discarded via a generation-token check, no further messages sent for the abandoned turn), not physically aborting the outbound Anthropic/ElevenLabs HTTP/WS calls themselves (neither `persona-turn.ts` nor `tts.ts` accepts an `AbortSignal` — real, disclosed follow-up work). Frequent barge-in during a session therefore costs more in vendor spend/load than the client-visible behavior alone would suggest.
- Hold-to-think (suspends turn detection entirely, real ~45s auto-release) both client-side (`use-live-converse-session.ts`) and server-side (`turn-orchestrator.ts`'s own independent 45s timer — a real backstop for a dropped connection or crashed client where `hold_end` never arrives at all, not merely a slow one), preserving the single `hasFloor` check from docs/adr/0002. **Found and fixed during this ticket's own review:** the client's first draft of `hasFloor` only excluded the `'thinking'` phase (copied verbatim from the scripted demo, which never had a separate `'speaking'` phase) — it didn't exclude `'speaking'`, so a hold could start while she was still mid-line, silently violating ADR-0002. Fixed to `phase === 'listening' && holdSeen`.
- `voice-connection.ts`'s extension with the new message types (mobile)
- `pcm-encode.ts`'s conversion logic (float frames → mono → 16-bit PCM → base64) — real and unit-tested, but not called by anything (see above)
- `use-tts-playback.ts`'s sequential playback/queueing logic — real and unit-tested against a fake player
- `use-live-converse-session.ts` — real and unit-tested against a fake `VoiceConnection` message stream

**Not built at all, not just unverified:**
- The mic → `audio_chunk` send path — no live raw-PCM source exists in this dependency stack (see above)
- Real per-session credential issuance from app-service (pre-existing gap, ARCHITECTURE.md §6) — as a direct consequence, `use-live-converse-session.ts` is not wired into `converse-screen.tsx`; the shipped screen still runs the scripted demo (`use-converse-session.ts`) unchanged

**Not verified, cannot be verified in this environment** (no physical device, microphone, or speaker exist here):
- Whether audio actually round-trips correctly end to end (blocked on the above, even in principle)
- Echo cancellation (structurally absent, see above — not just untested, actually not implemented)
- Barge-in's actual perceived responsiveness
- Hold-to-think's real-device timing/UX
- `data:` URI playback support
- The six-timestamp numbers actually landing in PRD §7.3's 700-900ms target

This is the same disclosure posture as docs/adr/0014/0015/0016 for #15-17, extended to cover a much larger fraction of this ticket's own AC list, per the explicit scope agreed for #18 specifically. Unlike #15-17, this ticket's own screen-level AC (a live Converse experience) is **not met** — what's delivered is every real, testable building block for it, correctly assembled and unit-tested in isolation, blocked from end-to-end activation by two structural gaps neither of which this ticket's scope covers.
