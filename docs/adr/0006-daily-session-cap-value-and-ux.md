# Daily session cap: default of 1, and reusing the Tomorrow screen as the "come back tomorrow" UX

**Status:** accepted, cap value provisional pending real vendor cost confirmation

Ticket #24's AC #2 explicitly leaves both the exact cap value and the UX for hitting it as open design questions this ticket has to decide, not just implement a backend limit for.

**Cap value — decision: default `DAILY_SESSION_CAP=1`.** PRD §9 gives the actual numbers: "A power user at two sessions a day on the premium stack costs $13.67/month against a $12 subscription." That's the PRD's own cited failure case — two sessions/day breaks the unit economics. At the same premium per-session ceiling ($0.228, PRD §9), one session/day costs ≈$6.84/month, comfortably under the $12 subscription. So the PRD's own math places the actual breakeven between one and two sessions/day, and one session/day is what genuinely bounds COGS under the subscription price — not an arbitrary round number. Configurable via `DAILY_SESSION_CAP` (`app-service/src/env.ts`), not hardcoded, per AC #4, so it can be adjusted as `voice_cost_model.xlsx`'s vendor costs change without a code change.

**UX — decision: hitting the cap redirects to the existing Tomorrow screen instead of a new screen or an error state.** `mobile/src/features/open/use-open-screen.ts`'s `useOpenAnswerHandler` calls `POST /sessions`; on a 429 with `code: 'daily_cap_reached'`, it routes to `/tomorrow` rather than `/converse`. The Tomorrow screen's pre-existing fixture copy (`tomorrow-fixture.ts`, from ticket #7) already reads: "No homework. Come back tomorrow. One session a day. Distributed practice beats massed practice." — this is *exactly* the "come back tomorrow as pedagogically correct, not a paywall-flavored restriction" framing AC #3 asks for, word-for-word close to the reasoning in PRD §9 itself. Building a second screen or a distinct error message to say the same thing would duplicate content that already exists and already has the right tone.

**Reasoning for server-side enforcement being load-bearing, not just UX:** `sessions.ts`'s `createSession` checks `countSessionsToday` (a real query against `sessions.started_at`, using the database's own clock via `date_trunc('day', now())`, not a client- or app-supplied timestamp a modified client could spoof) *before* running scenario selection or writing anything, and throws `DailySessionCapReachedError` — translated by `server.ts` into a 429, never a silent no-op. A direct `POST /sessions` call with no client involved at all hits the same check (verified: `server.test.ts`'s "a direct API call cannot bypass it" test, and a curl-driven smoke test against the compiled build).

**Consequences:** the cap counts *sessions started*, not sessions completed or minutes spoken — a learner who starts a session and immediately abandons it still consumes their daily cap. This is the literal reading of "daily session cap" per the ticket and PRD §9 (which frames the cost driver as "per 8-minute session," i.e., session count, not partial usage), but if real usage data later shows premature abandonment being unfairly capped, revisit whether the check should instead key off `sessions.ended_at` or elapsed duration. `DAILY_SESSION_CAP=1` is provisional in the same sense `RETENTION_DAYS`/`READINESS_MIN_EXPOSURES`/etc. are (see ADRs 0004/0005) — derived from the PRD's own stated numbers, not confirmed against real per-vendor billing yet.
