# Introducing the three difficulty dials, the heritage-speaker calibration variant, and the CEFR-informed taxonomy reorder

**Status:** accepted

Ticket #36 asks for a heritage-speaker calibration variant with distinct dial defaults and a reordered structures-taxonomy priority, "built on the multi-persona machinery from the second-persona ticket" (docs/adr/0023). This records what turned out to be a larger prerequisite than the ticket text alone suggests, and the concrete values chosen.

## The three dials (PRD §5.2) have never been implemented as data, by any ticket

PRD §5.2: "Difficulty is not one number. Three independent axes, **stored per session**" — comprehension load, production demand, repair behaviour, each 1-5. `sessions.calibration` (ticket #19) has carried exactly one value since it was created: `complicationLevel` (docs/adr/0005, which explicitly scoped itself to that one field and never touches the dials). No ticket between #19 and #35 wrote a comprehension-load, production-demand, or repair-behaviour value anywhere. So there was no existing "standard partner-learner calibration" for a heritage variant to diverge *from* in running code — only PRD's descriptive table, and (usefully) `mobile/src/features/address-book/address-book-fixture.ts`'s already-committed `dials: [2, 2, 1]` for Валентина, which this ADR treats as the closest thing to an existing product decision on her defaults and adopts directly, rather than inventing new numbers the mockup didn't already imply.

This ticket is therefore the one that introduces the dial system as real, storable data for the first time — `sessions.calibration` gains `comprehensionLoad`/`productionDemand`/`repairBehaviour` (1-5 integers) alongside `complicationLevel`, written at session creation (`sessions.ts`'s `createSession`) from the learner's `calibration_variant`.

## `learners.calibration_variant`: a new per-learner segment flag

Distinct from the *persona* (Валентина vs. Елена, docs/adr/0023) and distinct from *complication level* (which scenario ladder step, ADR-0005) — this is which **calibration profile** a learner's sessions draw their dial defaults from, independent of both. `calibration_variant TEXT NOT NULL DEFAULT 'partner_learner' CHECK (... IN ('partner_learner', 'heritage_speaker'))`, added the same idempotent way every other post-hoc column in this schema is (`learners.audio_sampling_consent_at`'s own precedent). Settable at onboarding (`POST /learners` gains an optional `calibrationVariant` field, same pattern ticket #30 used for `cyrillicLiterate`/`translitEnabled`) and via a dedicated `PATCH /learners/:id/calibration-variant` endpoint for flipping an existing test account — the granular-endpoint pattern this codebase already uses (`/learners/:id/audio-sampling-consent`), and directly what UAT #1 asks for ("Set a test account to the heritage-speaker variant").

## Dial defaults chosen

| Dial | `partner_learner` | `heritage_speaker` | Why |
|---|---|---|---|
| Comprehension load | 2 (Валентина's own fixture value) | **4** | PRD's own 1-5 description ("natural speed, regional idiom, elision" at 5) describes exactly what a heritage speaker's ear is already used to from childhood exposure — starting them low here would be teaching to a gap they don't have. |
| Production demand | 2 | **1** | The AC's own framing: "already listens well but produces little." PRD's 1 ("fragments accepted") meets the learner where their actual output ability is; starting higher (as their comprehension might superficially suggest) would demand fluency they don't yet have and risk exactly the discouragement backchanneling-first design (PRD §5.6) exists to avoid. |
| Repair behaviour | 1 | **1**, unchanged | Kept low deliberately, not varied: a heritage speaker's fragile, low-volume production is *more* likely to be misparsed by her turn-detection/comprehension than a confident partner-learner's clearer attempts, and PRD's 5 ("does not adjust; asks again the same way") is a resilience-testing setting this profile has no use for — the goal here is building production confidence, not stress-testing repair. |

Comprehension load and production demand move in *opposite* directions from the partner-learner default — the actual "noticeably different" (UAT #1) signature of a receptive-strong/productive-weak learner, not just a uniform difficulty bump.

## Structures-taxonomy priority: CEFR-informed reorder, a real exported module, deliberately not wired into scenario selection

PRD §5.8's order — aspect, motion verbs, stress placement, register, case government — is the one PRD §14 risk #9 itself names as suspect: "owner's own gaps become the product's priorities... audit against external reference (CEFR descriptors, ТРКИ syllabus, a teacher's view) rather than felt difficulty." `app-service/src/structure-taxonomy.ts` exports both orders by `calibration_variant`, keyed on the same canonical `structureKey` strings scenario content and the eval golden set already use (`aspect_perfective`, `verbs_of_motion`, `stress_placement`, `register`, `case_government` — no new vocabulary invented).

**Heritage reorder:** `register`, `case_government`, `aspect_perfective`, `verbs_of_motion`, `stress_placement`. Reasoning, cited to CEFR rather than felt difficulty per the AC's own instruction:

- **Register first.** The CEFR framework's Sociolinguistic Appropriateness descriptor scale treats command of register/politeness distinctions as a *productive*, comparatively late-maturing skill, distinct from and often lagging well behind basic comprehension or vocabulary range at the same overall level — which matches heritage speakers' well-documented profile precisely: native-level receptive recognition of formality, paired with weak controlled *production* of it, because home input skews informal/familial and rarely required sustained вы-register output.
- **Case government second.** Widely documented in heritage-language-acquisition research as a "fossilization" pattern: heritage speakers frequently default toward nominative/accusative and flatten oblique-case marking under real-time production pressure, even while recognizing correct forms receptively without difficulty — again a production-specific gap CEFR's own receptive/productive skill split predicts, not a comprehension one.
- **Aspect, motion verbs, stress lower**, not absent — these are comparatively more perceptually/lexically anchored categories (each verb pair is a distinct, memorable lexeme rather than an abstract agreement rule), so natural exposure tends to leave heritage speakers relatively more stable here even in production, versus the two more abstract, socially-governed categories above.

**Honest boundary on precision:** the case-government fossilization claim is general heritage-language-acquisition literature, not a specific citable CEFR passage or a verified ТРКИ syllabus section — this environment has no way to check either against a primary source with real confidence, and fabricating a specific citation would be worse than being plain about the reasoning's actual grounding. The Sociolinguistic Appropriateness scale's existence and general emphasis is accurately described above without claiming a page-level citation.

**Deliberately not wired into scenario selection.** `scenario-selector.ts`'s `selectNextScenario` picks scenarios by repetition-exposure (least-recently-used) and complication level by recent performance (ADR-0005) — it has no structure-priority input today, and no AC of this ticket asks for one (AC #3 asks for the priority order to exist and be "traceable to the external reference," AC #4 only asks that avoidance detection keep working against it — see below). Threading a real priority-weighted tie-break into an already-tested selection algorithm is real, separate scope this ticket doesn't name; `structure-taxonomy.ts` is built as a genuine, tested, real data artifact (the same class of deliverable golden-set.ts's own PRD §5.8-cited distribution comment already is), not wired further than that. A natural next step, left for whichever ticket actually asks for it.

## Avoidance detection under the reordered taxonomy (AC #4)

`avoidance-detection.ts`'s `detectAvoidance`/`detectAndRecordAvoidance` never read a priority list at all — they diff a session's *authored* target (`scenario_complications.target_structure_key`, set once per scenario by content authoring) against that session's real observations, purely by `structureKey` string equality. Reordering the priority list changes which `structureKey` a heritage-tuned scenario *should* eventually target (a content-authoring decision, per the point above), but the detection mechanism itself is order-agnostic by construction — it was never coupled to a global ordering to begin with. AC #4 is satisfied by this being true, verified directly with a test that runs avoidance detection against a heritage-priority-ordered structure key and confirms nothing about the mechanism cares.
