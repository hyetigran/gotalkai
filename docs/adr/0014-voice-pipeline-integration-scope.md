# Voice pipeline integration (#15-18): scope, ElevenLabs protocol notes, and the on-device gap

**Status:** accepted

Tickets #15 (STT integration), #16 (stress annotation), #17 (TTS integration), and #18 (full pipeline live in Converse) were all blocked on #13 (vendor bake-off) until the product owner explicitly decided to skip the bake-off and commit to ElevenLabs for both STT and TTS under a moved-up deadline (docs/adr/0013). This ADR covers all four — they're tightly coupled (one pipeline) and share the same environmental gap, so one shared record beats four near-duplicate ones.

## The on-device gap (applies to all four tickets)

This environment has no physical device, no microphone, no speaker, and no native Russian speaker available for review. Every one of these tickets' own UAT sections explicitly requires physical-device testing ("On a physical device...", "On a physical iOS device...") or native-speaker judgment (#16: "Have a native Russian speaker review the output stress marks"). Per explicit product-owner direction, the scope for all four tickets here is: **build everything that is genuinely code and unit-testable — vendor integration modules, algorithms, mobile-side wiring — and disclose exactly what still needs a real device/microphone/speaker/native speaker before it can be considered actually verified.** This mirrors the established pattern from ticket #14/#28 (no `ANTHROPIC_API_KEY` in this environment) and #31 (BIPA legal review) — build the honest, achievable core; don't fabricate verification that didn't happen.

Concretely, per ticket:
- **#15 (STT)**: the ElevenLabs realtime-STT client module and VAD gate are real, unit-tested code. What's unverified: real microphone audio actually producing sensible transcripts/confidence values, and VAD thresholds tuned against real ambient noise (the `speechThresholdRms` value has no universally-correct default — see vad.ts).
- **#16 (stress annotation)**: the dictionary+statistical-model pipeline and IPA-tag emission are real, unit-tested code. What's unverified: a native speaker's actual judgment on stress placement correctness (this ticket's own Pass bar).
- **#17 (TTS)**: the ElevenLabs TTS client module (sentence chunking, character-alignment capture) is real, unit-tested code. What's unverified: audible playback quality, whether playback genuinely coexists with concurrent mic capture on-device, and perceived streaming latency.
- **#18 (full pipeline)**: almost entirely on-device, real-time behavior — echo cancellation via `react-native-webrtc`, barge-in, hold-to-think against real turn detection, six-timestamp logging on real turns. The mobile-side wiring code can be written, but very little of ticket #18's own AC list is meaningfully verifiable without a physical device actually running a live conversation.

## ElevenLabs realtime STT: protocol details (verified against current public API docs, 2026-07-29)

The official `@elevenlabs/elevenlabs-js` SDK (v2.59.0) wraps the batch `speechToText.convert` endpoint but has **no realtime WebSocket client** — only the message *type* definitions are exported (`v1SpeechToTextRealtime` namespace). `voice-service/src/stt.ts` opens the connection directly via `ws` (already a dependency, used server-side in `server.ts`), hand-rolling the protocol:

- **URL**: `wss://api.elevenlabs.io/v1/speech-to-text/realtime`
- **Auth**: `xi-api-key` header (server-side use — the `token` query-param variant is documented for client-side/browser use, not applicable here per ARCHITECTURE.md §6's boundary: provider keys never reach the mobile client)
- **Session config**: passed as URL query parameters at connect time, not a separate message — `model_id`, `language_code`, `include_timestamps`, `commit_strategy`, `vad_threshold`, etc. `stt.ts`'s `buildSttUrl` sets `model_id=scribe_v2`, `language_code=ru`, `include_timestamps=true` (the last one is load-bearing: without it, the server sends plain `final_transcript` with no `words[].logprob`, silently losing the confidence signal ticket #15 exists to plumb through)
- **Wire format is snake_case JSON**, not the SDK's camelCased TypeScript types (which describe the SDK's own post-processed shape for a client that doesn't exist for this endpoint) — confirmed against ElevenLabs' AsyncAPI spec. Client sends exactly one message shape (`input_audio_chunk`: `message_type`, `audio_base_64`, `sample_rate`, `commit`); server sends `partial_transcript`, `final_transcript`/`final_transcript_with_timestamps`, `session_started`, and several distinctly-named error payloads (`auth_error`, `quota_exceeded_error`, etc.) — `stt.ts` treats any `message_type` containing `"error"` as an error rather than enumerating every specific error variant, since the handling (surface it via `onError`) is the same regardless of which one occurred.

## VAD: local energy-threshold gate, not delegated to the vendor's own VAD

ElevenLabs' realtime endpoint has its own built-in VAD (`commit_strategy=vad`), but it decides when to *finalize a transcript segment*, not whether audio was sent to the vendor at all — and ElevenLabs bills "per minute of audio processed" (docs/adr/0013), meaning silence streamed to an open connection is still billed regardless of the vendor's own VAD later deciding it wasn't speech. PRD §9's "VAD-gated STT" cost requirement and ARCHITECTURE.md's pipeline diagram (`VAD → streaming STT`, VAD as its own upstream stage) both point at gating *before* the network call, not after. `vad.ts`'s `VadGate` is a local, cheap, energy-threshold state machine (instant speech-start, hysteresis/hangover on speech-end) deciding when to call `sendAudioChunk` at all — independent of and upstream from whatever ElevenLabs does internally.

## #15's explicit scope boundary vs. #18

Ticket #15's own AC #4 says the STT confidence signal must "exist and be plumbed here" but is "wired fully in the 'Full pipeline live in Converse' ticket (#18)." AC #1 ("Real mic audio... streams into the voice service and out to the chosen STT vendor") doesn't carry that same explicit deferral clause in its own text — this is a real interpretive extension, not a clean one-to-one disclosure, worth stating plainly rather than implying it's already settled by AC #4's wording alone.

The reasoning for reading AC #1 the same way: "streams into the voice service" describes a wire connecting the mobile client's mic audio, through `server.ts`'s existing WebSocket protocol, to the STT vendor — but #18 is titled "Full pipeline live in Converse... replacing the Wave 1 scripted demo," and its own AC #1 is explicitly "Converse screen... drives real audio in and out through the full pipeline (tickets #14 persona LLM, #15 STT, #16 stress annotation, #17 TTS) instead of the scripted script." That sentence only makes sense if #15 (along with #14/#16/#17) hands #18 a *component*, not an already-wired mic-to-vendor pipe — #18 is precisely the ticket that assembles the components into one live connection. Extending server.ts's client-facing protocol to carry real audio frames, before three of the four pipeline stages it would need to hand those frames to (#16, #17, and #18's own turn-detection/barge-in logic) exist yet, would mean either building throwaway plumbing now or half-wiring #18's actual job piecemeal across multiple tickets' diffs. Building the STT+VAD module as a clean, tested, injectable-client unit — ready for #18 to call — is the reading this ADR commits to, but it is a reading, not something AC #1's own text settles unambiguously by itself.
