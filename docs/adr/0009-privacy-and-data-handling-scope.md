# Ticket #31 scope: what's built now vs. what needs legal/audio-storage design first

**Status:** accepted

Ticket #31 (Privacy & data handling, PRD §12.2) has four ACs. This records why one is deliberately not attempted here, and what the other three actually mean given no audio-storage subsystem exists yet.

**Decision:** build the parts of #31 that are genuinely achievable against this codebase's real state today; explicitly flag the one that isn't, rather than fabricating it.

- **AC #1 (BIPA/biometric-privacy-law check before any audio storage ships) — not attempted.** This is a legal judgment call ("checked and addressed... by the team's chosen legal reference"), not an engineering task. No audio storage exists yet to check against, and no legal review has been commissioned. **This must go through a human/lawyer before any real audio capture ships** — nothing in this ticket's build should be read as having satisfied it.
- **AC #2 (2–5% sampling, gated behind separate consent) — built as pure policy, not wired to a live capture path.** `src/audio-sampling.ts`'s `shouldSampleSession(hasConsent, rate, random)` encodes both halves (no consent → never sampled; consent → real random draw against the configured rate) and is tested statistically against real `Math.random`, not just its injected seams. `AUDIO_SAMPLE_RATE` (env.ts, default 0.03) is the configured rate. Consent is recorded via `POST /learners/:id/audio-sampling-consent` → `learners.audio_sampling_consent_at`, a separate explicit action from account creation — there is no ToS-acceptance flow in this codebase at all, so "separate from ToS" is trivially true today, not a real design decision being tested. There is no audio-storage subsystem (ARCHITECTURE.md hasn't designed one) for this function to actually gate — it's the policy the future capture path must call, built ahead of that path per this ticket's directed scope.
- **AC #3 (sampled-audio retention materially shorter than metadata retention) — reserved value, not enforced.** `AUDIO_SAMPLE_RETENTION_DAYS` (env.ts, default 30 vs. `RETENTION_DAYS`'s 180) exists as a policy value only. There is no audio-storage table for a retention sweep (`src/retention.ts`'s pattern) to run against, so nothing enforces it yet. This AC is **not** satisfied by this ticket — only its eventual target value is reserved.
- **AC #4 (single deletion path clears memories, audio, transcripts together, verified to cascade) — built and verified for every data category that actually exists.** `src/privacy.ts`'s `deleteLearner` is one `DELETE FROM learners WHERE id = $1`; schema.sql's existing `ON DELETE CASCADE` graph (tickets #19-#22) does the rest — `learner_structures`, `observations`, `persona_memories`, `sessions` (itself cascading to `turns`/`debrief_items`) all disappear structurally, not via a list of deletes this function has to keep in sync. `src/privacy.test.ts` proves this by inserting a row into every one of those tables, calling `deleteLearner` once, and querying each table directly afterward — matching UAT #3's own instruction ("query the database... directly, don't just trust the... success message"). There is no audio table yet; when one is added it must hang off `learners` (directly or transitively) so this same single statement keeps covering it automatically.

**Reasoning:** the alternative to this split was inventing an audio-storage schema this ticket has no design mandate for, just to make AC #2/#3/#4 look fully done — that would produce code with no real backing requirement, and worse, would let AC #1's actual gate (a real legal check) get quietly absorbed into "it's built, ship it." Keeping the gap explicit here is the whole point: BIPA-class review is meant to happen *before* the thing it's reviewing exists in production, not be back-filled once it's already built.

**Consequences:** whoever picks up real audio capture must (a) complete AC #1's legal review first, using this document as the pointer to what's already built for AC #2 (`shouldSampleSession`) and AC #3 (`AUDIO_SAMPLE_RETENTION_DAYS`); (b) call `shouldSampleSession` from wherever audio capture is decided per-session, gated on `learners.audio_sampling_consent_at`; (c) build the actual retention sweep once an audio table exists, and make sure that table cascades from `learners` so `deleteLearner` keeps being the single deletion path AC #4 requires — not a second path someone has to remember.
