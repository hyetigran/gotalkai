# Observability: scope, the missing turn-persistence link, and what has no real backend in this environment

**Status:** accepted

Ticket #29 (PRD §11) asks for two genuinely separate alerting systems (health/quality), the eval harness pointed at production hourly as a canary, four derived quality metrics needing no manual labelling, live per-session/per-user cost tracking, and per-turn tracing with P95 alerting. This records the concrete decisions made to build all of that against what this codebase and environment actually have today, and discloses what's real versus stubbed.

## The prerequisite this ticket found and had to build first: nothing wrote to `turns`

`schema.sql`'s `turns` table (ticket #19) has carried `timings JSONB` and `revealed BOOLEAN` since it was created, and `turn-orchestrator.ts` (ticket #18) has computed the full six-timestamp log per turn since then too — but grepping the whole codebase turns up no `INSERT INTO turns` anywhere. `sendTurnComplete` only ever sent `timestamps` over the WebSocket to the client; nothing persisted a row. ARCHITECTURE.md §3's own sequence description ("voice service ... posts turn artefacts / timings back through app service after turns") names the intended shape but it was never wired. Every one of this ticket's four derived metrics, its cost tracking, and its tracing all read from `turns` rows that didn't exist before this ticket — so building the write path (`POST /sessions/:id/turns` in app-service, an injected `recordTurn` dep in `turn-orchestrator.ts`) is this ticket's own necessary foundation, not scope creep borrowed from #18. It's built the same way every vendor call in this pipeline is: injected, DI-tested, and — for the real HTTP call to app-service from voice-service — fire-and-forget with a logged, swallowed failure, so an app-service outage degrades observability, not the live conversation (ARCHITECTURE.md's own rule: "Voice has zero DB mid-turn").

## Health vs. quality: two call sites, not two views of one table

AC #1 asks for alerting paths that are "genuinely separate ... not one dashboard with two tabs." This is built as two independent functions with no shared code path: `sendHealthAlert` (voice-service's `alerting.ts`, app-service's `observability/alerting.ts`) posts to `HEALTH_ALERT_WEBHOOK_URL` and is the only thing the canary and the P95/cost checks ever call. `sendQualityReport` (app-service only) posts to a separate `QUALITY_REPORT_WEBHOOK_URL` and is the only thing the derived-metrics digest calls — unconditionally, every run, regardless of what the numbers say, because a quality report is a standing digest, not a threshold check. There is no code path that can call both from the same trigger. Per PRD's own text, the canary is the one deliberate exception inside "quality" that pages anyway ("Canary assertion failures *do* page, because they are deterministic") — it is wired to `sendHealthAlert`, not `sendQualityReport`, precisely because a mechanical golden-set assertion failing is a deterministic fact, not a subjective sampled read.

**No real paging or webhook vendor account exists in this environment** (no PagerDuty/Opsgenie, no Slack/Discord webhook). Both alert functions take a plain webhook URL and POST a JSON payload — the generic integration point any of those products expects on the receiving end — and both no-op with a console-logged line when their URL env var is unset, so tests and local dev don't require one. This is the same disclosure posture as every other unavailable external account in this codebase (docs/adr/0013's skipped bake-off, docs/adr/0016's un-auditioned voice ID): the seam is real and correctly shaped, delivery to an actual pager is unverified.

## Tracing: spans are computed and structured, not shipped to a vendor

"Trace shape: one trace per session, span per turn, child spans per pipeline stage" is built from the six timestamps that already exist (`t0`–`t5`) — `voice-service/src/tracing.ts`'s `buildTurnSpans` turns them into named child spans (`stt`, `persona_llm`, `stress_annotation`, `tts_first_audio`) with start offsets and durations, and `logTrace` emits one structured JSON line per turn (`[trace] { sessionId, turnId, spans }`) — a real, versioned shape, ready for a collector to ingest. **No tracing backend (Honeycomb, Datadog, an OTel collector) exists or has an account in this environment**, so nothing actually ships anywhere yet; `logTrace` is the export seam, not a claim that traces are queryable today. P95 is computed in app-service (`observability/p95.ts`) from *persisted* turns over a trailing window, not per-turn in the hot path — a single turn has no percentile of its own, so this reads as a genuinely periodic check (same shape as the derived-metrics digest and the cost rollup below), alerting via `sendHealthAlert` when a stage's P95 crosses `P95_LATENCY_BUDGET_MS`.

## Derived metrics: what each one is actually computed from, and the one still blocked by an existing disclosed gap

All four (`app-service/src/observability/metrics.ts`) read only `turns`/`sessions` columns already being written — no manual labelling step exists to skip.

- **Reveal rate**: `count(revealed) / count(persona turns)`. Requires the learner's tap-to-reveal action to reach the server. A real endpoint exists for this (`PATCH /turns/:id/reveal`) and is unit-tested, but **no mobile client calls it yet** — this is the same structural gap docs/adr/0017 already disclosed (`use-live-converse-session.ts` isn't wired into `converse-screen.tsx`, itself blocked on no live mic-capture source and no per-session credential issuance). This ticket doesn't reopen or re-disclose that gap as new; it inherits it. Reveal rate will read as real zeros until #17's gap closes, not because this ticket's own plumbing is incomplete.
- **False interruption rate**: PRD's own definition ("learner resumes within ~500ms of her starting") is a judgment call to make precise. Read as: a barge-in event whose delta from the interrupted persona turn's `t5FirstAudio` (when her audio actually started) is under 500ms. `turn-orchestrator.ts` tracks the most recently *persisted* persona turn's id and `t5FirstAudio` on the instance; `handleBargeIn` computes the delta and fires `recordInterruption` (a new `POST /turns/:id/interruption`, storing `interrupted_after_ms`) when it was genuinely mid-speech. The rate is `count(interrupted_after_ms < 500) / count(interrupted_after_ms IS NOT NULL)`, grouped by `sessions.calibration->>'complicationLevel'` per AC's "track per level."
  - **Real bug found and fixed while building this**: the first draft persisted the persona row only after `synthesizeSpeech`'s *entire* promise resolved (all sentences fetched). But a barge-in can only happen while `state === 'speaking'` — exactly the window *before* that promise resolves — so the row (and its real turn id) would never exist yet at the moment any genuine interruption occurred; every real barge-in would have found nothing to attach to. Fixed by persisting at the *first* TTS chunk instead (where `t5FirstAudio` is genuinely defined — messages.ts's own "first chunk ready" doc comment — and everything else needed, text/usage/character-count, is already known by then). A second, related bug: `state` flips to `'speaking'` slightly before the first chunk arrives (synthesis is still fetching sentence one), and a barge-in landing in that narrow gap would otherwise misattribute to the *previous* turn's still-set marker — fixed by clearing the marker the instant `state` becomes `'speaking'`, both here and in the safety-response path below.
  - **Scope narrowing, disclosed rather than silent**: the out-of-character safety-response path (ticket #27) does not call `recordTurn` at all — persisting a distress-disclosure's actual content deserves its own explicit product decision (`turns.content` currently stores every ordinary learner turn already, but a triggering disclosure is a different sensitivity class PRD's own safety-detection.ts comment already flags for logging specifically), not a default made silently inside this ticket. A barge-in during a safety response therefore also can't misattribute to it (there's no marker to misattribute — see the fix above) or to an earlier real turn (the marker is cleared).
- **Abandonment turn**: no explicit "session ended early" flag exists (there's no "session complete" message anywhere in the protocol either — sessions just stop). Read as the distribution of each session's final turn index, grouped by `calibration->>'complicationLevel'` — "which dial setting loses people" per PRD, derived from where turns actually stop, not a separate completion marker this ticket would have had to invent.
- **Repeat-request rate**: PRD calls this "a free proxy," distinct from reveal rate and from the STT-confidence-triggered "didn't catch that" mechanic (which is about the *system* not hearing the learner, the opposite direction). Read as learner turns matching a small fixed set of Russian repeat-request cue phrases (что?, повтори, не поняла, не понял, ещё раз) — a keyword heuristic, disclosed as exactly that, not an NLU classifier. Coarse by design; PRD itself says to "keep both [this and reveal rate], they disagree usefully."

## Cost: an estimate from captured usage, not a reconciled vendor invoice

PRD's own text gives the reason live tracking has to be an estimate: "Vendor invoices arrive four weeks late." `voice-service/src/cost.ts` prices the three PRD §9-named cost drivers — persona LLM tokens (from the Anthropic response's own `usage` field, now captured in `persona-turn.ts`'s result rather than discarded), TTS characters (text length at the point `synthesizeSpeech` is called), and STT audio duration (a new per-turn accumulator in `turn-orchestrator.ts`, summing exactly the frame durations actually forwarded to the STT vendor) — against fixed list-price constants. **Not captured**: the safety-detection classifier call's own (small) token cost, and the eval judge's — both real Anthropic calls with a real cost, but secondary line items next to the three PRD names explicitly, narrowed out of this pass rather than silently missed. `app-service/src/observability/cost.ts` rolls per-learner `cost_usd` up over a trailing 30 days and pages via `sendHealthAlert` when it crosses `SUBSCRIPTION_PRICE_USD` — PRD's Health line explicitly includes "within budget," and per-user cost overrun is exactly that, not a quality signal.

## The hourly canary: no separate "production" model deployment exists to point at

PRD says "point the eval harness at production." There is no staging/production split for the persona model itself — `generatePersonaTurn` (ticket #14) already calls the real Anthropic API directly, in-process, the same call production traffic makes; there is no separate stand-in. "A provider ships an update, and nothing errors" (PRD's own framing for why this canary exists) is about that real vendor endpoint silently changing behavior — which is exactly what a canary run of `runEval` against the live Anthropic client already exercises, whether or not a deployed voice-service process is also fronting a WebSocket somewhere. `eval/canary.ts` picks a fixed five-entry subset of the golden set by id (not the full 20, per AC's "~$0.20/day" budget framing); `eval/run-canary.ts` runs `runEval` against just that subset and calls `sendHealthAlert` on any gate failure. Scheduled hourly via a GitLab CI **Pipeline Schedule** (configured in project settings, not expressible in `.gitlab-ci.yml` alone) triggering the new `eval:canary` job. **Same disclosed gap as docs/adr/0012**: this GitLab project has no CI runners registered, confirmed via the API — the schedule and job are written correctly and will run the moment a runner exists, but that has not been, and cannot be, verified to actually execute in this environment.

The P95 budget check and the cost-threshold check (AC #4/#5) need the exact same kind of periodic trigger — `app-service/src/observability/run-checks.ts` computes both (plus the unconditional quality digest) but was, in an earlier draft of this work, wired to nothing at all: a real gap a first-pass Spec review of this diff caught, not something disclosed on purpose. Fixed the same way as the canary: `.gitlab-ci.yml`'s `observability:run-checks` job, gated on its own `$OBSERVABILITY_SCHEDULE` custom variable (a separate GitLab CI Pipeline Schedule from the canary's, since P95/cost/quality don't need hourly granularity the way a provider-degradation canary does), running `pnpm observability:run-checks`. Same CI-runner disclosure as above applies here too.
