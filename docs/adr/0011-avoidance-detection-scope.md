# Avoidance detection: diffs classified observations, not raw transcript text

**Status:** accepted

Ticket #23 (PRD §5.5): "we inject target structures at session start, so we can diff intent against production and detect what the learner steered around." This records what "production" means here, and what's deliberately left out.

**Decision:** `detectAndRecordAvoidance` (`app-service/src/avoidance-detection.ts`) diffs a session's target structure against the `structureKey`s already present in that session's `observations` rows — not against raw turn text. If the target structure never appears in any observation for the session (success, failure, or otherwise), it's avoidance; if it appears at all, it isn't, regardless of whether the attempt succeeded.

**What "target structure" means concretely:** a new nullable `scenario_complications.target_structure_key` column, set on the one scenario level whose authored copy already unambiguously demands a structure — `cat_vet_visit` level 1 ("she will ask you to tell it back to her," i.e. narrate a sequence of completed past events): `'aspect_perfective'`. Chosen from PRD §5.8/§7.10's own named examples of structures that survive ASR normalization (aspect, motion verbs) — not an arbitrary pick, and not force-fit onto scenario levels whose copy doesn't actually demand a specific structure.

**Reasoning:** classifying raw learner speech/text into structure keys (did this turn exhibit perfective aspect, present tense, a specific case, etc.) is a real NLP problem — closer in scope to the stress-annotation-tier work (§7.4, blocked on #13's bake-off) than to "diff intent against production." `observations-request.ts`'s own existing comment already names the component that does this classification: "the post-session analyser, ticket #14+" — a separate, not-yet-built piece. Ticket #23's actual, buildable scope is the diff *itself*: given the analyser's already-classified output for a session, was the target structure ever attempted. Building a real classifier here would mean inventing the analyser's job without the analyser existing, which is a much larger, differently-scoped undertaking than this ticket asks for.

**Consequences:**
- Until the analyser exists and actually calls `POST /sessions/:id/observations` with real classified turns, avoidance detection has nothing real to diff against — it will always resolve to "avoided" for any session at a targeted complication level with no observations submitted, since "call POST /sessions/:id/observations with the target structure present" is the only way to prove non-avoidance today. This is expected, not a bug: it's the same "buildable ahead of the pipeline" posture ticket #14 took with `generatePersonaTurn`.
- `learner_structures.avoidances` is now written for the first time (previously read by `scenario-selector.ts`'s `getPerformanceRate` but never incremented anywhere). `exposures`, `attempts`, `successes`, and `stability` on the same table remain unwritten by any code in this repo — that gap predates this ticket and is out of its scope; `computeReadinessForStructure` (`debrief.ts`) and `getPerformanceRate` (`scenario-selector.ts`) will keep reading zeros for those columns until whatever writes real observations for successes/attempts is built (again, the analyser).
- Only one complication level (`cat_vet_visit` level 1) is seeded with a `target_structure_key` — a coverage floor, not a ceiling. AC #1's own phrasing ("e.g. a scenario designed to demand...") is illustrative, and one worked example proves the mechanism end to end without force-fitting a target onto scenario copy that doesn't actually demand a specific structure (`tea_visit`'s levels, and `cat_vet_visit`'s other two, don't). As more scenario content is authored, more levels should get a `target_structure_key` where their copy genuinely calls for one — this is a content-authoring task, not a code change, since `detectAndRecordAvoidance` already reads whatever's seeded.
- "Distinct framing" (AC #3) is achieved by setting `detail.tag: 'you steered around this'` directly on the avoidance observation — the mobile Debrief screen's `mapDebriefItemToPattern` (mobile/src/features/debrief/map-debrief-item.ts) already renders `detail.tag` verbatim when present, falling back to a generic "impeded communication" tag only when it's absent. No mobile code changes were needed.
