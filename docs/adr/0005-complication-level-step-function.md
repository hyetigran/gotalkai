# Complication level: a step function relative to the previous session, not an absolute mapping

**Status:** accepted, provisional thresholds

PRD §5.3 says scenarios "scale by complication, not vocabulary" — the same scene at increasing demand levels (her tea example: offers tea → out of the tea you like → offended you didn't visit). Ticket #21's UAT is explicit about the *shape* of the response, not the exact numbers: "confirm the complication level and scenario selection visibly respond to the prior session's real performance (harder complication after success, same/lower after struggle) rather than advancing on a fixed schedule." Ticket #21's AC #1 names five `learner_structures` columns the selector should read: `exposures`, `attempts`, `successes`, `avoidances`, `stability`.

**Decision:** complication level is a step relative to the learner's most recent session's level (read back from `sessions.calibration->>'complicationLevel'`), not an absolute function of some global proficiency score:

- No performance signal yet (a first session, or no `learner_structures` rows with `attempts + avoidances > 0`) → hold at the previous level (0 for a genuinely first session).
- `performanceRate >= SUCCESS_ESCALATE_THRESHOLD` (default 0.7, `SUM(successes) / SUM(attempts + avoidances)` across all the learner's tracked structures) → escalate one level, capped at `COMPLICATION_LEVELS - 1`.
- `performanceRate < STRUGGLE_DEESCALATE_THRESHOLD` (default 0.35) → de-escalate one level, floored at 0.
- Otherwise → hold.

**Reasoning:** the UAT frames this as directional and session-relative ("harder complication after success"), not as "learner X should always see level Y." A step function tied to the previous session is the literal, minimal reading of that requirement, and it composes naturally with `sessions.calibration` (ticket #19's own column for "the calibration actually used for that session") without inventing a new global proficiency score the PRD doesn't ask for. Aggregating across *all* the learner's `learner_structures` rows (not per-structure, per-scenario) is a simplification: the real signal ought to be scoped to structures relevant to the specific scenario being considered, but scenario-to-structure tagging doesn't exist yet (scenarios are hand-authored fixtures — src/seed-scenarios.ts — with no structure metadata) and adding it would be inventing scope this ticket didn't ask for.

**On the five named columns — three used, two deliberately not:**

- `successes`, `attempts`, `avoidances` are used directly: `performanceRate = successes / (attempts + avoidances)`. Folding `avoidances` into the denominator, rather than ignoring it, follows PRD §5.5 directly — "You steered around this is more useful than you got this wrong" treats avoidance as at least as strong a struggle signal as an outright error, so it should count against readiness to escalate the same way a failed attempt does, not be invisible to the algorithm.
- `exposures` is **not** read separately. Ticket #20's `computeReadiness` (debrief ranking) already uses `exposures` as a minimum-exposure gate for a different purpose (whether a *specific structure* is ripe for debrief feedback). Here, `attempts` already implies at least that much exposure to a structure the learner actually engaged with; a bare exposure count with no attempt attached carries no performance signal this algorithm could act on, so including it would mean adding an input with no defined effect on the output — that's cargo-culting the column, not using it.
- `stability` is **not** read. No ticket built so far writes a real value to `learner_structures.stability` — it defaults to 0 (ticket #19) and nothing computes it (PRD §8 assigns that job to "the debrief," but ticket #20's debrief ranking reads `learner_structures` for `readiness`, it doesn't write `stability` back). Reading a column no pipeline populates would make the algorithm silently see 0 forever in real usage, which is worse than not reading it: it would look like real behavior while being dead weight. Revisit once some ticket actually computes and writes `stability`.

**Consequences:** `SUCCESS_ESCALATE_THRESHOLD`, `STRUGGLE_DEESCALATE_THRESHOLD`, and `COMPLICATION_LEVELS` (`app-service/src/scenario-selection.ts`) are provisional, tunable constants, not a recorded product decision on the exact numbers — revisit once real session data exists to check whether 70%/35% actually track "ready for harder" / "struggling" in practice. If scenario-specific structure tagging is added later, `getPerformanceRate`'s aggregate-across-everything approach (`app-service/src/scenario-selector.ts`) should narrow to just the structures the specific candidate scenario exercises. If a future ticket starts writing real `stability` values, folding it in as an escalation-confidence gate (e.g. don't escalate on a high `performanceRate` alone if `stability` is still low) is the natural next step.
