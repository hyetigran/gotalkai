# Stress annotation: dictionary-only, honest "unresolved" tail, naive IPA adapter

**Status:** accepted

Ticket #16 (PRD §7.4) specifies "dictionary lookup for the high-frequency core, a RUAccent-class statistical model for the tail." This records why only the first half was actually built, and the judgment calls behind the parts that were.

## No RUAccent-class model exists for this stack

RUAccent (and its predecessor, StressRNN) are Python packages with no Node.js port and no hosted API. Using either here would mean either running a Python subprocess/microservice, or exporting model weights to ONNX and running them via `onnxruntime-node` — real infrastructure (model files, hosting, a verified inference pipeline) this environment doesn't have and can't responsibly fabricate. Rather than build a fake "statistical model" that's really an unreliable heuristic wearing a label, out-of-dictionary words are honestly reported as `unresolved` (`stress-annotation.ts`'s `resolveWordStress`) — no stress mark is guessed. PRD §7.4 itself is the reason not to guess: "a mis-stressed word in a pronunciation-teaching app actively teaches the error." An honest gap is better than a confident wrong answer in a product whose entire premise is correct pronunciation modeling.

**Consequence:** the "tail" (out-of-dictionary words) isn't covered at all yet. `annotateText`'s `unresolvedWords` list exists specifically so this gap is visible (loggable, expandable) rather than silently absorbed. Whoever picks up real tail coverage should either integrate a real hosted model (Python microservice call, or an ONNX export of RUAccent/StressRNN) or accept a narrower initial dictionary and grow it from production `unresolvedWords` logs.

## Dictionary: hand-curated from this codebase's own real content

`dictionary.ts`'s ~80 entries are drawn from words this codebase's own dialogue actually uses (persona.ts's identity prompt, the eval harness's golden-set.ts, app-service's seed-scenarios.ts) plus common function words — not a bundled corpus (none exists for this stack, see above) and not invented vocabulary. Deliberately excludes ambiguous homographs whose stress depends on grammatical case/meaning (PRD §7.5's own bake-off list names these) — a wrong guess there is worse than falling through to the honest-unresolved path. Monosyllabic words (≤1 vowel) and ё-bearing words are deliberately absent from the dictionary — both resolve by rule (`stress-annotation.ts`), not lookup, so a dictionary entry for either would be dead weight; `dictionary.test.ts` enforces this mechanically.

## ё handling satisfies AC #4 by construction, not by a bolted-on check

PRD §7.4/AC #4: "`ё` written explicitly wherever semantically present, never silently dropped." `resolveWordStress` never removes or replaces any character from its input except through one narrow, curated path — it only ever *inserts* a combining accent otherwise. An `ё` present in the input is therefore structurally guaranteed to survive; there's no code path that could silently drop it, which is a stronger guarantee than a separate "check ё wasn't lost" assertion would be.

**Revised after review — preserving isn't the same as restoring.** An earlier draft of this ADR only claimed the narrower guarantee above: that an `ё` already in the input survives. It said nothing about text that arrives with `ё` already flattened to `е`, which is extremely common in casual Russian writing and plausible in LLM-generated text (training data is full of it). PRD's own AC #4 text — "written explicitly wherever semantically present" — reads as the broader claim, not just "preserved when present." `dictionary.ts`'s new `YO_RESTORATION` table closes part of that gap: a short, curated list of е-spelled words whose only correct spelling has `ё`, with no competing real word spelled the same way without it (e.g. "еще" → "ещё", "живет" → "живёт"). It deliberately excludes genuine homograph pairs where dropping `ё` produces a *different, valid* word — `все` (all, plural) vs `всё` (everything), `берет` (a beret) vs `берёт` (takes) — restoring those automatically would silently corrupt correct text, which is worse than the gap this table closes. This is still not a general е→ё model (that's the same class of problem as the missing statistical stress model, addressed above) — just a short, high-confidence, expandable list, checked *before* every other resolution step in `resolveWordStress` since a spelling correction is a different, prior question from whether the corrected result needs a stress mark.

## Vendor stress-mark format: ElevenLabs needs IPA phoneme tags, not `+`/U+0301

Already established in docs/adr/0013: ElevenLabs' documented pronunciation-control mechanism is SSML `<phoneme alphabet="ipa" ph="...">` tags, requiring the `eleven_v3` model for non-English IPA. `stress-annotation.ts` still produces the internal representation as Cyrillic text with a combining acute accent (U+0301) — the standard, unambiguous way to mark Russian stress in plain text, and the representation this ADR's dictionary is authored in — and `phoneme-format.ts` is a separate adapter converting that internal form to ElevenLabs' wire format.

**The Cyrillic→IPA mapping in `phoneme-format.ts` is a simplified, per-letter table, not a real phonemic transcription.** It does not model vowel reduction (akanie/ikanie — unstressed о sounding like [ə]/[ɐ], unstressed е like [ɪ]) or consonant palatalization assimilation, both real Russian phonetic phenomena a production-quality system needs. What it does get right, because it's the only thing this table is actually built to guarantee: the stress marker (ˈ) lands immediately before the correct syllable's phoneme — which is this ticket's actual, literal AC. Full phonetic fidelity beyond stress placement is a disclosed gap requiring either a real grapheme-to-phoneme library or native-speaker-verified output against real ElevenLabs audio — the same on-device/native-speaker verification gap docs/adr/0014 already discloses for this whole ticket batch.

## Wiring into the live pipeline is #18's job, same pattern as #15

`annotateText` isn't called anywhere in `server.ts` yet. Consistent with docs/adr/0014's established scope boundary for #15: every persona LLM turn passing through stress annotation before reaching TTS is part of assembling the *whole* live pipeline (#18), not a piece to duplicate into #16's own diff.
